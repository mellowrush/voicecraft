# AI Vendor selection (OpenAI/Anthropic) is an app-level concern, not a core concept

Supporting multiple AI Vendors (OpenAI, Anthropic) touches only the Mac app's Rust layer — the vendor tag, the per-vendor Keychain entry, and the per-vendor default model all live in `packages/app/src-tauri`. Core's `Engine`/`Provider` contract does not change: a Provider is still a single `(prompt, opts) => text/stream` function, and per ADR 0002 it already owns its auth/secrets entirely opaquely to core. We considered giving core a `vendor` concept (e.g. a `Provider` factory keyed by vendor) so vendor-specific prompt tuning would be possible, but rejected it — ADR 0002 already decided prompt construction must not diverge per backend, and core has no reason to know which HTTP API a Provider calls underneath.

We introduce **AI Vendor** as a new term distinct from **Provider**, because the two were already colliding in code (`call_provider`, `ProviderCallError`, `provider-api-key` Keychain account, `provider_error`) before there was more than one vendor to be ambiguous about. "Backend" was considered and rejected as the new name — it's already in Provider's own glossary `_Avoid_` list, so reusing it would just relocate the ambiguity rather than resolve it.

Two follow-on decisions, recorded here since they're easy to get wrong on a fresh read of the code:

- **Keychain scheme.** The existing single `provider-api-key` account (service `com.voicecraft.app`) is replaced with one account per Vendor (`openai-api-key`, `anthropic-api-key`). On first launch after upgrade, an existing `provider-api-key` entry is migrated to the `openai` account (OpenAI was the only Vendor that ever existed) and the old account is not proactively deleted — the migration is additive/idempotent so a rollback or partial launch never loses the key.
- **Selected-Vendor storage.** Follows the precedent set for `lastUsedProfileId` (issue #21's decision against a separate settings store): the selected Vendor is a field in the same `voice-profiles.json` blob, read via the same synchronous, no-webview-round-trip path the hotkey's background thread already uses for `last_used_profile_id`.
