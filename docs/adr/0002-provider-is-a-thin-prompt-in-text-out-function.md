# Provider is a thin `(prompt) => text/stream` function; prompt construction stays in core

The Engine/API contract makes the injected `Provider` a thin function that only ever receives a finished prompt string — it never sees the `VoiceProfile`, mode, or context, and never participates in prompt construction. All prompt-building (turning a Voice Profile + mode + context into an actual prompt) lives inside the Engine itself. We considered letting providers receive the structured request and build their own prompts, which would let a provider tune prompts to its specific model — but rejected it: it would let prompt-construction logic silently diverge between providers, making behavior inconsistent across the pluggable backends this contract exists to support. This also means the Provider function *is* the whole injected-interface story for platform/secrets abstraction — there is deliberately no separate `SecretsStore` interface, since core never talks to a backend directly and so never needs credentials.
